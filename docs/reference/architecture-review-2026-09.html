Bottom line

Verdict

Ship it, then pay down one structural debt before the second harness lands. Hygiene is top-decile: clean ruff and mypy, 863 fast tests in 13s, digest-pinned base images, SHA-pinned CI actions, least-privilege workflow tokens, a supply-chain job, and a test suite that locks invariants (dry-run/real-launch argv parity, allowlist-not-denylist for agent-initiated changes) rather than just lines. Very little of this repo is accidental.

The systemic problem is that harness-neutrality is aspirational, not enforced. docs/architecture.md calls it "the most important architectural rule" and an "architectural constant" that "cannot be relaxed." It is currently violated in eight core modules, including the launch path, the credential broker and the bundled config defaults. This is cheap to fix today and expensive the moment a second adapter exists — which is exactly the v1.0 plan.

The second-order risk is process weight, not code. 6,000 lines of docs against 9,200 lines of source, with 253 D-NNN, 131 F-X-NN and 107 Stage N references embedded in comments. The decision log earns its keep; the review-finding IDs and stage numbers do not — 131 of them resolve to nothing a reader can look up.

Finding group 1

Architectural cohesion

The three-layer model (core / adapter / backend) is the right decomposition for this problem and the control-layering write-up (enforcement / behavioural / cooperation) is genuinely sharp thinking. The gap is between the model and its realisation.

CriticalHarness-neutrality is violated across the core, including the launch path cli/_launch.py · broker.py · images.py · harness_config.py · preset_config.py · init_wizard.py · wake.py · session_log.py

architecture.md: "Whizzard core must remain harness-neutral. It must know nothing about Hermes internals. This is the most important architectural rule." The launch core opens by importing the Hermes adapter directly and branches on its concrete type:

# whizzard/cli/_launch.py
from whizzard.adapters.hermes import (
    MEDIATION_PLACEHOLDER, MediationContext, OneCLIContext, cleanup_managed_dir,
)
...
if isinstance(adapter, HermesAdapter):
    adapter.allow_ephemeral = allow_ephemeral

It is not an isolated slip. The pattern repeats through the core:

  • broker.py hardcodes ANTHROPIC_API_KEY / ANTHROPIC_TOKEN / CLAUDE_CODE_OAUTH_TOKEN in, per its own comment, "Hermes's own priority order." The credential-resolution order of one harness lives in the policy engine.
  • images.py exports WHIZZARD_HERMES_IMAGE; docker_cmd.py re-exports it.
  • harness_config.py and preset_config.py ship hermes-cell / hermes as bundled defaults, including a hermes_home field the generic schema does not model.
  • init_wizard.py builds the Hermes image and clones ~/.hermes/ as core setup flow.
  • MediationContext and OneCLIContext — pure egress-plumbing types with nothing Hermes-specific in them — are defined inside the Hermes adapter and imported upward by core. The dependency arrow points the wrong way.

Today this costs nothing because there is one adapter. It becomes the dominant refactor cost the moment OpenClaw or NanoClaw lands, which the roadmap puts at v1.0 — and every one of these sites is a place a second adapter will either fork the logic or silently inherit Hermes semantics.

Fix Move MediationContext/OneCLIContext to adapters/base.py (or a new egress/ module) so core stops importing from adapters.hermes. Move the credential candidate list behind an adapter method (adapter.model_credential_candidates()). Move bundled Hermes config/preset/image defaults into the adapter package and have core ask the registry for them. Then add a one-line fitness test: assert not grep("hermes", core_modules) — the rule becomes enforced instead of asserted.
CriticalThe adapter Protocol is a partial fiction — four attributes are set on adapters that the contract never declares cli/_launch.py, docker_cmd.py vs adapters/base.py

Core writes session_id, web_search, mediation, onecli and allow_ephemeral onto the adapter object. None appear in the HarnessAdapter Protocol. Each write carries a suppression:

adapter.session_id = session_id   # type: ignore[attr-defined]
adapter.web_search = prof.web_search   # type: ignore[attr-defined]
adapter.mediation = MediationContext(...)  # type: ignore[attr-defined]
# and, in docker_cmd.py:
allow_ephemeral=bool(getattr(adapter, "allow_ephemeral", False))

The effect is that mypy whizzard passes while the real core↔adapter interface is undocumented and unchecked. A third-party adapter written against the published Protocol — which docs/decisions.md D-160 proposes shipping as a versioned contributor artifact — would launch and then fail at runtime, because the Protocol omits the launch-state injection core actually performs. This is the contract you are asking outside contributors to build against.

Fix Replace the attribute injection with one explicit call: adapter.bind_session(SessionContext(...)), declared on the Protocol, carrying session_id, web_search, mediation, onecli and allow_ephemeral. Deletes five type: ignores and makes the adapter contract true.
Majorbuild_run_argv mutates the host filesystem, which is why dry-run needs a cleanup call docker_cmd.py:build_run_argv

A function named "build argv" creates directories and touches files:

sess_dir.mkdir(parents=True, exist_ok=True)
(sess_dir / "audit.jsonl").touch(exist_ok=True)
request_dir(session_id).mkdir(parents=True, exist_ok=True)
SESSIONS_LOG.touch(exist_ok=True)

The consequence is visible in the dry-run path, which has to reach back and undo the side effect it did not ask for:

# cli/_launch.py, dry-run branch
# building the argv above authored the managed-scope dir as a side effect;
# dry-run exits before the finally that normally reaps it, so remove it here
cleanup_managed_dir(session_id)

That comment is the design smell, written out longhand. Worse, it is a security-relevant surface: --dry-run is the command a cautious user runs to inspect containment without side effects, and it currently has them.

Fix Split into prepare_session_state(session_id) -> SessionPaths (side-effecting, real launches only) and build_run_argv(..., paths) (pure). Dry-run calls only the pure half and needs no cleanup. The existing test_dry_run_parity.py already guards the argv half — extend it to assert no filesystem writes.
MajorThe adapter factory maps a category to an implementation — type: "agent" always means Hermes adapters/__init__.py:build_adapter

build_adapter dispatches on type, where "shell" → generic and "agent" → Hermes, with the honest comment "When future agent adapters land, a sub-discriminator will be needed." But type is a user-editable field in harnesses.json, so the config schema already has a public shape that cannot express "which agent." Adding OpenClaw is therefore a breaking config change, not an additive one — precisely the outcome the versioned schema_version machinery elsewhere in this repo was built to avoid.

Fix Add an optional adapter: "hermes" field now, defaulting to hermes when type=="agent", and dispatch on a registry dict. Backwards-compatible today, no schema break later. Ten lines.
MajorProfile encodes network posture twice, and the derived field is permanently typed | None config.py:Profile

network_enabled: bool and network_mode: str | None overlap. __post_init__ derives one from the other, so network_mode is never None after construction — yet its type says otherwise forever, and every consumer compares it against bare string literals with no exhaustiveness checking. The validator then has to re-couple them by hand (network_mode in ("mediated","onecli","hybrid") and not network_enabled → error).

The cost showed up in build_run_argv, where the comment has to shout:

# NOTE: hybrid MUST be in this branch — omitting it makes the cell fall
# through to the default bridge (full egress), which fails OPEN.

A five-member string union with a fail-open default branch is the wrong shape for the field that decides whether a sandbox has unrestricted internet.

Fix Make network_mode: Literal["none","open","mediated","onecli","hybrid"] the single source of truth; derive network_enabled as a read-only property for the legacy JSON shape. Then make the build_run_argv dispatch exhaustive with an else: raise so a future mode cannot fail open.
MinorThree parallel vocabularies for the same concepts repo-wide

The sandbox is called cell in code, sandbox in the README and known_issues.md (which needs a terminology note to reconcile them), and container in architecture.md. The credential posture is native to users and mediated internally — a deliberate, documented D-191 choice, but it means every reader holds a translation table. And the abandoned Osmotiq rename left live artifacts: 8 OIQ references in tests and pyproject.toml, plus this in the adapter contract's own docstring:

adapters/base.py
"The adapter is the seam between Whizzard (which provides containment
 and policy enforcement) and Whizzard (which orchestrates an agent
 harness inside the contained execution cell)."

A sed sweep collapsed two distinct nouns into one and left the sentence meaningless — in the file you intend to publish as the contributor-facing adapter contract.

Fix Pick sandbox (the user-facing word) and sweep cell out of code and comments; keep native/mediated but state the mapping once in architecture.md rather than in six comments. Fix the base.py docstring and the stale OIQ strings.
Finding group 2

File tree organisation

The repo root is exemplary — LICENSE, SECURITY, CONTRIBUTING, CODE_OF_CONDUCT, CHANGELOG, ROADMAP, a Makefile that actually works, example configs under config/, and a docs/ tree with a validated decision log. Majorinit_wizard.py is 1,805 lines — 20% of the whole package in one file whizzard/init_wizard.py

It holds prompt primitives, five wizard steps, three sub-flows, four config writers, the Docker build runner, the Hermes profile cloner and the idempotency check. Its largest single block (_step_4_custom_preset_subflow and neighbours) runs ~100 lines apiece. It is also the module with the most untested lines in the package (123 missed).

You have already solved this problem once, well: cli/ was split into _shared, _launch, _session plus one module per sub-app, and it reads cleanly. The wizard is the same shape of problem and should get the same treatment.

Fix whizzard/setup/ with prompts.py, writers.py, state.py and steps/step1_image.py …, mirroring the cli/ split. No behaviour change, and it makes the untested branches individually reachable.
Majordocker_cmd.py carries five unrelated responsibilities whizzard/docker_cmd.py (684 lines)

Daemon health classification, image inspection, Dockerfile text parsing (parse_dockerfile_base_pin — an image-provenance concern that belongs in images.py), argv construction, audit-log credential scrubbing, and the blocking session runner. Four of the five are read-only queries; one launches and supervises a container. They change for different reasons and are tested by different files.

It also re-exports four image constants purely to dodge an import cycle ("avoids an import cycle: docker_cmd imports adapters, and the adapters now reference these too"), which is a cycle the layer split above dissolves.

Fix Split into runtime/docker_probe.py (available / daemon_status / image_exists / image_inspect), runtime/docker_run.py (build_run_argv + run_shell) and move parse_dockerfile_base_pin + the scrubber to images.py and core/session_log.py respectively.
MinorIn-sandbox code lives in two different places, neither of them obvious whizzard/mcp_server.py vs whizzard/_dockerfiles/broker/proxy.py

Two files in this package never run on the host. mcp_server.py sits at the top level among host modules and is COPY'd into the sandbox image; proxy.py sits under _dockerfiles/broker/. Both are deliberately dependency-free of the whizzard package for good reasons that the Dockerfile explains — "the full whizzard package is deliberately NOT installed — it would expose the policy layer to a compromised agent" — but nothing in the tree communicates that constraint. A future contributor adding from whizzard.config import … to mcp_server.py would break the sandbox image and pass every host test.

Fix One whizzard/sandbox/ package holding both, with a module docstring stating the no-host-imports rule, plus a test asserting neither file imports whizzard.*.
Minorconfig.py is both the profiles module and the shared-config toolbox config.py ← preset_config.py, harness_config.py

preset_config.py imports validate_schema_version and validate_positive_int_or_none from config.py, so the preset loader depends on the profile module for generic primitives. config.py also owns WHIZZARD_HOME/STATE_DIR/LOGS_DIR, which every module needs. Three distinct concerns — path constants, validation primitives, profile parsing — in one name.

Related: tests/ is 36 flat files mirroring the flat source tree, so it inherits the same lack of shape. Split the source and the test tree follows for free.

Fix core/paths.py (constants), core/_schema.py (validators), core/profiles.py (parsing).
Finding group 3

Code quality

CriticalThe container holding the real credential is the only unhardened container Whizzard launches broker.py:start_broker

The sandbox gets seven hardening flags. The broker — which reads your live Anthropic key off disk and holds it in memory for the session — gets none:

# the sandbox (docker_cmd.build_run_argv)
--user … --cap-drop=ALL --security-opt no-new-privileges --read-only
--tmpfs … --memory … --pids-limit …

# the broker (broker.start_broker)
docker run -d --name … --label … --network … --restart no
           -e BROKER_AUTH_SCHEME=… -v :/run/broker/key:ro  ← that's all

The image does set USER nobody, so this is defence-in-depth rather than an open door — but the asymmetry is backwards relative to the threat model. The broker is also reachable unauthenticated by anything on the per-session internal network, and in hybrid mode the OneCLI shim shares that network with it. And proxy.py does body = await request.read() with no size bound on a container with no --memory cap, so a compromised sandbox can OOM the credential holder.

Fix Apply the same baseline to the broker and shim: --cap-drop=ALL, --security-opt no-new-privileges, --read-only, --pids-limit, --memory 256m. Bound the proxy request body (client_max_size on the aiohttp app). Roughly a ten-line change, and it makes the hardening story uniform.
CriticalAuth scheme is inferred from a substring of the secret's name broker.py:_infer_scheme 
def _infer_scheme(secret_name: str) -> str:
    upper = secret_name.upper()
    if "OAUTH" in upper or "TOKEN" in upper:
        return "bearer"
    return "api_key"

This decides whether the real credential is injected as x-api-key or as Authorization: Bearer. A user whose harnesses.json names the secret ANTHROPIC_API_TOKEN — an entirely natural name for an API key — gets it sent as a Bearer token plus an unwanted anthropic-beta: oauth-… header, and the failure surfaces as an opaque upstream 401 several layers away from the cause. The same string is carried across a container boundary into BROKER_AUTH_SCHEME, so the wrong guess propagates.

Note the hardcoded candidate list in the same module already pairs each name with its correct scheme explicitly. Only the user-declared model_credential.secret path falls back to guessing.

Fix Add an explicit model_credential.scheme: "api_key" | "bearer" to the harness schema, validated in harness_config.py. Keep the heuristic only as an unvalidated default and log which scheme was chosen at launch so a mismatch is diagnosable.

MajorFour near-identical config loaders, each re-implementing the same eight steps config.py · mounts.py · harness_config.py · preset_config.py

Each of the four does: resolve path → exists-check → json.loads with its own JSONDecodeError wrap → top-level-is-object check → validate_schema_version → sub-key-is-object check → non-empty check → per-entry parse → its own *ConfigError. That is ~40 lines of identical scaffolding duplicated four times, with four exception types that callers must catch separately (_launch.py catches three of them in sequence).

The modelling is inconsistent too: profiles, mounts and presets return frozen dataclasses; harness_config.get_harness_config returns a raw dict. That untyped dict is the one core then mutates (harness_cfg["platforms"] = …) and reads security-relevant keys from (harness_cfg.get("model_credential")) — so the least-typed config is the most security-relevant one.

Fix One core/_schema.py with load_registry(path, section, parse_entry, error_cls); each module keeps only its parse_entry. Give harnesses a frozen HarnessSpec dataclass like its three siblings, with platforms handled by dataclasses.replace instead of dict mutation. Have the four error types share a ConfigError base so callers catch once.
Major131 comment references that resolve to nothing, plus 107 build-order breadcrumbs repo-wide, whizzard/**.py

Three reference systems are embedded in source comments:

  • 253 D-NNN — resolve to docs/decisions.md, validated in CI by scripts/validate_decisions.py. These earn their keep. Keep them.
  • 131 F-X-NN (F-F-08, F-C-04, F-B-01…) — review-round finding IDs. grep across docs/ and CHANGELOG.md returns zero hits. They are unresolvable to anyone who wasn't in the review.

The underlying comments are frequently excellent — they explain why, which is the hard part and which most codebases skip. The prefixes are the problem, not the prose. At ~22% comment density the noise is load-bearing on readability.

Fix Strip the F-X-NN and Stage N prefixes and keep the sentence that follows ("F-F-06: if the container just self-exited this tick…" → "If the container just self-exited this tick…"). Mechanical, ~250 edits, and it removes the whole class. Add a CONTRIBUTING line: comments cite D-NNN or nothing.
MinorDocumentation drift: four statements that no longer match the code README.md · Dockerfile · base.py · ci.yml
  • README overclaims time-bounding. "Sessions are time-bounded. Every session carries a duration cap and an idle cap." The shipped default profile has duration_seconds=None and idle_timeout_seconds=None — and monitor_and_enforce short-circuits to a bare proc.wait() when both are None, so the enforcement loop never runs for the default profile. The README's own profile table says "none" in the Time-cap column, so the bullet contradicts the table three screens above it. For a containment tool, that is the one kind of overstatement worth zero tolerance.
  • Dockerfile pin instructions name the wrong Debian. "To refresh the pin: docker pull debian:12-slim" — the FROM is debian:13-slim. Following the comment re-pins you to the wrong major.
  • Supply-chain CI audits a different dependency set than ships. ci.yml installs 'mcp>=1.0' unpinned while pyproject.toml ships mcp>=1.0,<2 — so pip-audit resolves mcp 2.x, which known_issues.md documents as the version that breaks the sandbox MCP server.

MinorCross-module private import, and import-time path binding broker.py:35 · safety.py:47 · tests/conftest.py

from whizzard.docker_cmd import _docker_env — a leading-underscore symbol consumed across a module boundary. Three modules now shell out to Docker (docker_cmd, broker, onecli_gateway), each with its own subprocess wrapper; that is a shared runtime/docker.py asking to exist.

Separately, safety.py binds HOME = Path.home() and builds its blocklists at import time, and mutates those module-level lists in an if is_windows(): block at import. The cost is visible in tests/conftest.py, which has to set WHIZZARD_HOME at conftest import — before any test module's from whizzard… runs — and then adds an autouse guard fixture to catch regressions. That is a workaround for a design choice, and it is documented as such in the conftest docstring.

Fix Promote _docker_env into a shared runtime/docker.py alongside a single run_docker() helper. Make the safety blocklists a function of home (blocklists(home: Path) -> Blocklists) resolved per call, which also deletes the Windows import-time mutation and most of the conftest gymnastics.
Credit where due

What's genuinely good — and rarer than it looks

  • Invariant tests, not just coverage. test_dry_run_parity.py asserts the preview argv and the real argv differ only by an explicit allowlist, on the stated grounds that "a preview that lies is a security bug." That is the right test to have written, and almost nobody writes it.
  • Allowlist chosen over denylist, with the reasoning preserved. AGENT_ALLOWED_CHANGES replaced an earlier AGENT_DENIED_CHANGES because a denylist means any newly-added field is agent-callable by default. The comment records the replacement, so the next contributor can't quietly regress it.
  • The sandbox is not trusted to report its own state. Request resolutions are written to a host-only store under STATE_DIR, outside the sandbox-writable mount, specifically so a sandbox-claimed status of "applied" can't bypass operator review — with a path-traversal guard on the one identifier the sandbox influences. This is the correct instinct applied in the right place.
  • Dependency injection where it buys testability. monitor_and_enforce takes now, sampler and warner as parameters, which is why the enforcement module sits at 93% without a Docker daemon.
  • Monotonic vs wall clock, correctly separated. The audit log gets time.time(); the enforcement loop gets time.monotonic(), so laptop sleep and NTP steps can't fire spurious expiry. Most projects find this in production.
  • Structural, not string, URL pinning in the proxy. URL.build(host=UPSTREAM_HOST, …) makes authority injection unrepresentable rather than filtered.
  • Supply chain taken seriously. Digest-pinned base images with a CI check that they stay pinned, SHA-pinned GitHub Actions, persist-credentials: false, workflow-level contents: read, pip-audit with each ignore individually justified, Debian packages over pip for the two security-critical containers.
  • An honest known-issues register. docs/known_issues.md documents the deferred-execution gap, DNS exfiltration, and unverified Windows support — and the README repeats them under "Scope and limitations" rather than burying them. A security tool that states what it does not do is worth more than one that doesn't.
