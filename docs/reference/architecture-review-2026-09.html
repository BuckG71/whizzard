Assessment

Whizzard at v0.1.0

An evaluation of three things: architectural cohesiveness, file-tree organisation, and code quality. What follows is a judgment on what the codebase is — its shape, where it holds together, where it doesn't, and what that predicts. It is not a work plan.

Overall

Summary judgment

A codebase with a genuinely good architectural idea, executed unevenly — and unevenly in a legible pattern rather than a random one. Nothing here is rotten; one thing is structurally wrong, and it is the one thing the project says about itself most emphatically.

The single most useful thing I can tell you is that the quality of any given module in this repo is well predicted by how it came to exist. Modules that were specified once and built to that specification — safety, enforcement, requests, snapshot — are excellent: tight, well-tested, correct about the hard cases. Modules that accreted across successive build stages — docker_cmd, adjust, init_wizard, the Hermes adapter — are serviceable but overgrown, mixed in responsibility, and under-tested. That is a correctable pattern with an obvious cause, and it is much better news than uniform mediocrity would be.

Variable 1

Architectural cohesiveness

The conceptual model is sound, unusually well-articulated, and shows restraint that most projects in this space don't. The implementation is cohesive everywhere except one seam — and every breach at that seam points the same direction, which makes it a single structural fact rather than decay.

What's genuinely well-conceived

  • The core principle is an invariant, not a slogan. "Whizzard controls capabilities / agents request capabilities / agents do not grant themselves capabilities" is stated as three lines in architecture.md and is actually load-bearing in the code: the agent-callable change surface is an allowlist (AGENT_ALLOWED_CHANGES) that replaced an earlier denylist precisely because a denylist makes every newly-added field agent-callable by default. The reasoning is preserved in-comment so it can't be quietly regressed. Plenty of projects state a principle; few make it testable and then test it.
  • The control-layering model is the sharpest thinking in the repo. Splitting containment into enforcement (kernel/Docker, Whizzard-owned), behavioural (approval flows, harness-owned) and cooperation (the in-sandbox MCP surface) — with explicit ownership per layer and a stated rule against mixing them — is a clearer articulation than most tools in this category manage. It correctly identifies that these are different kinds of control, not different strengths of the same control.
  • It shows architectural restraint. The decision not to recreate harness-native dangerous-command approval is explicitly argued: "Recreating them would duplicate harness work and add surface area the harness already maintains." The pull toward owning the whole stack is strong and this project resisted it with a written rationale. That is a mature judgment, and it is the kind of thing that keeps a codebase small.
  • The trust boundary is drawn in the right place and defended consistently. Three independent examples: request resolutions are written to a host-only store outside the sandbox-writable mount, so a sandbox claiming its own request was "applied" can't bypass review; config write-protection is enforced at the safety-validation layer rather than the policy layer, because a policy-layer check could be overridden by policy; the full whizzard package is deliberately kept out of the sandbox image so a compromised agent can't read the policy engine. These are the same instinct applied three times in three places, correctly.

Where it doesn't hold — and it's one thing, not many

architecture.md is unusually emphatic on one point, calling it both "the most important architectural rule" and an "architectural constant" that "cannot be relaxed by future work":

Whizzard core must remain harness-neutral. It must know nothing about Hermes internals. […] No harness-specific logic belongs in Whizzard core. docs/architecture.md — "Architecture Layers" and "Architectural Constants"

As of this commit that claim is false. Eight core modules know about Hermes:

ModuleWhat it knows
cli/_launch.pyImports HermesAdapter and branches on isinstance; imports four symbols from adapters.hermes
broker.pyHardcodes the model-credential candidate list in, by its own comment, "Hermes's own priority order"
images.pyExports WHIZZARD_HERMES_IMAGE; docker_cmd re-exports it
harness_config.pyShips hermes-cell as a bundled default, with a hermes_home field the generic schema doesn't model
preset_config.pyShips a hermes preset as a bundled default
init_wizard.pyBuilds the Hermes image and clones ~/.hermes/ as core setup flow
wake.py · session_log.pyCarry Hermes-ephemeral session semantics

Three observations about how this is broken, which matter more than the count:

  • The dependency arrow points the wrong way at the load-bearing seam. MediationContext and OneCLIContext are pure egress-plumbing types with nothing Hermes-specific in them — and they are defined inside the Hermes adapter and imported upward by core. That is not a leak of detail into core; it is core depending on a concrete adapter for a shared abstraction.
  • The published contract is partly fiction. Core writes five attributes onto adapter objects — session_id, web_search, mediation, onecli, allow_ephemeral — that the HarnessAdapter Protocol never declares. Each is suppressed:
adapter.session_id = session_id      # type: ignore[attr-defined]
adapter.web_search = prof.web_search # type: ignore[attr-defined]
adapter.mediation = MediationContext(...) # type: ignore[attr-defined]
# docker_cmd.py:
allow_ephemeral=bool(getattr(adapter, "allow_ephemeral", False))

So mypy whizzard passes cleanly while the real core↔adapter interface is undocumented and unchecked. This matters more than an ordinary type hole because D-160 proposes publishing that Protocol as a versioned contributor-facing artifact — an adapter written against the contract as documented would launch and then fail.

  • The factory can't express the thing it's for. build_adapter dispatches on type, where "agent" maps unconditionally to Hermes, with the honest note that "a sub-discriminator will be needed" later. Because type is a user-editable field in harnesses.json, the config schema has already committed to a shape that can't say which agent — in a repo that otherwise versions every config schema specifically to avoid that.
  • But the leak is systematic, not entropic. Every violation runs toward Hermes. No core module knows about Discord, or the gateway's internals, or some unrelated third thing. This is not a codebase that lost its shape; it is an abstraction that was specified on paper before a second instance existed, then bent — carefully, and with each bend documented — to fit the one implementation that does exist. That is a recoverable position, and a different diagnosis from "the layering eroded."

Judgment

Cohesion is strong in conception and strong in the three-quarters of the implementation that doesn't touch the adapter seam. At that seam, harness-neutrality is currently a documented intention rather than an implemented property — and the architecture document asserts it as an implemented property. That gap between stated and actual invariant is the single most significant architectural fact about this repo right now.

Variable 2

File-tree organisation

Exemplary at the repo root — better than most funded projects. Layer-blind inside the package. And most tellingly, inconsistent with its own demonstrated instincts: the same author split cli/ well and left init_wizard.py at 1,805 lines.

The root is a model of its kind

LICENSE, SECURITY, CONTRIBUTING, CODE_OF_CONDUCT, CHANGELOG, ROADMAP, RELEASING, a Makefile whose targets actually work, example configs isolated under config/, a docs/ tree with a validated decision log, and a .github/ with issue templates, a PR template, CODEOWNERS and dependabot. Nothing missing; nothing extraneous; nothing in the wrong place. A contributor can orient in about ninety seconds. This is genuinely above the bar for a 0.1.0.

The package interior expresses no architecture

whizzard/ is twenty flat modules in which the policy core, the egress plumbing, code that runs inside the sandbox, and host orchestration all sit as peers:

green = tight & well-covered · blue = healthy · amber = mixed responsibility · red = overgrown · purple = runs inside the sandbox, not on the host
  • The tree can't be used to infer the architecture, which is the main job a tree has. architecture.md opens by defining three layers — core, adapter, execution backend — and the directory listing expresses exactly one of them (adapters/).
  • Two files that never run on the host live in two unrelated places. mcp_server.py sits at the package top level among host modules; _dockerfiles/broker/proxy.py sits under the Dockerfile directory. They share a critical constraint — neither may import whizzard.*, because the policy engine is deliberately kept out of the sandbox image — and nothing in the tree communicates it. A contributor adding from whizzard.config import … to mcp_server.py would break the sandbox image and pass every host test.
  • config.py carries three concerns under one name — path constants, generic validation primitives, and profile parsing — which is why preset_config.py imports its validators from the profiles module. Small, but it's the reason the config layer reads as tangled rather than parallel.
  • tests/ mirrors the source — 36 flat files. It inherits the shape rather than compounding the problem; it isn't independently disorganised.

The telling part: the instinct is present and was applied unevenly

This isn't a case of not knowing better. cli/ was split into _shared, _launch, _session plus one module per sub-app, and it reads cleanly — each file has one job and the package docstring maps them. adapters/ is a proper package with a Protocol, a factory and two implementations. The same treatment simply never reached init_wizard.py (which holds prompt primitives, five wizard steps, three sub-flows, four config writers, a Docker build runner and a profile cloner) or docker_cmd.py, whose own docstring names its accretion out loud:

"""Docker invocation for the execution cell.

Stage 1 baseline restrictions, Stage 2 mount handling, Stage 5 session
logging (container id capture via --cidfile, image id capture via
docker image inspect, JSONL log entries for start and end).
"""

Judgment

This is organisational debt, not organisational failure. Nothing is misfiled; a good deal is unfiled. The distinction matters for how worried to be: misfiled code misleads readers, unfiled code merely fails to help them. At a solo scale with one adapter it costs little. It becomes the dominant onboarding cost the moment a second person or a second harness arrives.

Variable 3

Code quality

High — in places notably higher than typical commercial code — and non-uniform in a way that is diagnostic rather than random. Quality tracks provenance: what was designed is excellent; what accreted across build stages carries every defect I found.

The strong evidence

  • Tests assert invariants, not lines. test_dry_run_parity.py locks that the --dry-run preview argv and the real launch argv differ only by an explicit allowlist, on the stated grounds that "a preview that lies is a security bug." That test exists because someone reasoned about what would make the tool dishonest rather than merely broken. Most codebases never write it.
  • Time is handled correctly, pre-emptively. The audit log takes time.time(); the enforcement loop takes time.monotonic(), so laptop sleep/wake and NTP steps can't fire spurious session expiry. That is usually a lesson learned from a production incident. Here it's in the first release with the reasoning written down.
  • Fail-closed is chosen consistently, including where it costs UX. A snapshot that can't be written aborts the launch rather than warning — because an agent with no readable snapshot is blind to its own boundaries. Broker start failure aborts. OneCLI unavailability aborts with two named alternatives rather than silently degrading. The default when something is uncertain is consistently "don't run."
  • Testability is designed in where it pays. monitor_and_enforce takes now, sampler and warner as injected callables, which is why the enforcement module reaches 93% coverage with no Docker daemon in the loop.
  • Some defences are structural rather than filtered. The broker proxy pins its upstream with URL.build(host=UPSTREAM_HOST, …), making authority injection unrepresentable rather than screened for. Similarly the sandbox request-id is validated as a single non-traversing path component before it can ever become a host path.
  • Comments explain why, which is the part that's hard and the part most codebases omit. The network_mode dispatch in build_run_argv carries a note that omitting the hybrid branch would fail open to the default bridge — exactly the kind of knowledge that otherwise lives in one person's head.

The weak evidence — and the pattern behind it

The defects are not scattered. They cluster in modules that were revisited across many build stages, which those modules advertise through their own stage-marker density:

ModuleStage refsLinesCondition
docker_cmd.py17684Five responsibilities: daemon probing, image inspection, Dockerfile text parsing, argv construction, session running
adjust.py10908Largest non-wizard module; 82% covered
adapters/hermes.py9987Adapter, profile creation, managed-scope authoring, gateway-lock parsing in one file

safety.py0328Specified once, built once — tight, 92% covered
enforcement.py0426Same — 93% covered, injected dependencies
  • Coverage is inverted against risk. broker.py sits at 36%, cli/_launch.py at 64%, cli/adjust.py at 18% — against safety.py 92% and enforcement.py 93%. The broker is the process that resolves and holds the live model credential, and its uncovered lines are specifically the partial-start rollback and the orphan reaper: the code that only runs when something has already gone wrong, and whose own failure leaves a credential-holding container and a plaintext key file behind. An 80% global floor is a reasonable gate, but the aggregate is hiding the distribution.
  • Two genuine latent defects, both on the credential path. The broker infers whether to send x-api-key or Authorization: Bearer by substring-matching the secret's name ("TOKEN" in upper), so a key legitimately named ANTHROPIC_API_TOKEN is transmitted as a Bearer token with an unwanted beta header — surfacing as an opaque upstream 401 far from its cause. Separately, the broker container is launched with none of the seven hardening flags the sandbox gets; its image sets USER nobody, so this is defence-in-depth rather than an open door, but the asymmetry runs opposite to the threat model — the most sensitive container is the least constrained.
  • A pure-sounding function isn't. build_run_argv creates directories and touches files on the host. The consequence is visible in the dry-run path, which reaches back to undo a side effect it never requested — meaning --dry-run, the command a cautious user runs to inspect containment without consequences, has them.
  • Four near-identical config loaders. Profiles, mounts, harnesses and presets each re-implement the same eight steps and raise their own error type (callers catch three in sequence). Three return frozen dataclasses; harness_config alone returns a raw dict — and that untyped dict is the one core mutates and reads security-relevant keys from. The least-typed config is the most security-relevant one.
  • Comment noise has accumulated past the useful threshold. At ~22% comment density the prose is mostly excellent, but three reference systems are embedded in it: 253 D-NNN refs (resolve to decisions.md, CI-validated — these earn their keep), 131 F-X-NN review-finding IDs (resolve to nothing — grep across docs/ and CHANGELOG.md returns zero), and 107 Stage N build-order breadcrumbs that are meaningless to anyone who joined after the fact.
  • Small documentation drift, one item of it substantive. The README asserts "Sessions are time-bounded. Every session carries a duration cap and an idle cap" — while the shipped default profile has neither, and monitor_and_enforce short-circuits to a bare proc.wait() when both are None. The README's own profile table says "none" in that column three screens above. For a containment tool this is the one category of inaccuracy worth zero tolerance, regardless of size.

Judgment

Take the designed modules alone and this is better code than most of what ships commercially in this category — the security reasoning in requests.py's trust boundary and the invariant tests in particular. Take the accreted modules and it's ordinary competent Python that grew past its structure. The two populations are clearly separable, which means the quality problem has a shape and an address rather than being diffuse.

Maturity profile

The process apparatus is scaled for a team; the codebase is scaled for one person. That mismatch buys something real and costs something real, and both are visible.

  • What it buys: traceability I could not get from most codebases. I was able to reconstruct the reasoning behind nearly every non-obvious design choice from the repo alone — why the agent-change surface is an allowlist, why credentials never enter the sandbox, why the OneCLI shim exists (the gateway's unauthenticated :10254 dashboard), why the base images are digest-pinned. That is rare and it is worth real money when a second contributor arrives or when someone audits this.
  • Honesty about its own gaps is a genuine asset. known_issues.md documents the deferred-execution hole, DNS exfiltration, and unverified Windows support, and the README repeats them under "Scope and limitations" rather than burying them. A security tool that states plainly what it does not do is worth more than one that doesn't — and this materially raises my confidence in the claims it does make.
  • What it costs: ceremony per change, and artifacts nobody maintains. The 131 unresolvable F-X-NN refs are the clearest symptom — a review-tracking scheme that outlived its index. The abandoned Osmotiq rename is another: it left eight stale OIQ strings and collapsed two distinct nouns into one in the adapter contract's own docstring, which now reads "the seam between Whizzard […] and Whizzard" — in the file slated to become the contributor-facing contract.
  • Three vocabularies coexist for one concept. The contained environment is cell in code, sandbox in the README (and known_issues.md needs an explicit terminology note to reconcile them), and container in architecture.md. The credential posture is native to users and mediated internally — a deliberate, documented choice, but every reader now carries a translation table.
Forecast

What this assessment predicts

The useful output of an assessment is where the thing strains under load. For this codebase the answer is unusually specific.

  • It absorbs almost any change cheaply — except one. New profiles, new network modes, new safety rules, new CLI verbs, new enforcement signals all have obvious homes and good test scaffolding. The second harness adapter does not. Every one of the eight neutrality violations is a site that will either fork or silently inherit Hermes semantics, and the Protocol that a new adapter would be written against omits five attributes core actually requires. The roadmap places that change at v1.0, which means the largest piece of architectural debt is due at the next milestone rather than eventually.
  • A second contributor pays the file-tree cost immediately. Today one person holds the layer model in their head and the flat tree costs nothing. The first outside PR that puts harness logic in core, or adds a host import to mcp_server.py, will pass CI — because the rules that would catch both are documented in prose and enforced nowhere.
  • The credential path is where an incident would come from. Not because it's badly designed — the broker architecture is sound and the isolated-network reasoning is careful — but because it combines the highest stakes with the lowest test coverage (36%) and the least container hardening. The untested lines are precisely the failure-recovery paths.
  • Nothing here suggests decay. No dead code of consequence, no abandoned abstractions, no comment/code contradictions beyond the four drift items, no test suite being worked around. The trajectory is a project that built carefully and outgrew its structure in two specific places — which is a much easier position to be in than the reverse.

If I had to summarise in three sentences

The architecture is well-conceived and shows judgment — particularly the control-layering model and the restraint about what not to build — but its single most emphatic self-claim, harness-neutrality, is not currently true. The file tree is excellent where a newcomer looks first and uninformative where they look second, and it's inconsistent with the author's own demonstrated instincts rather than ignorant of them. Code quality is high and cleanly bimodal: designed modules are better than commercial norm, accreted modules are ordinary, and every defect I found lives in the second group.
